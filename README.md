## 1. Архитектура и где живут заявки

Одностраничный лендинг на Server Components + один route handler `POST /api/lead`.
Страница статическая, но с ISR раз в час: даты «ближайшая обжарка / развозка / дедлайн заказов» считаются на сервере и не устаревают.

**Почему не SQLite/файл.** На Vercel файловая система read-only и ephemeral: запись в `./data/leads.sqlite` упадёт на проде, а если бы и прошла — каждый холодный старт получил бы свою пустую базу, и дедупликация между инстансами перестала бы работать. Поэтому:

1. **Telegram Bot API** — основной и надёжный канал: заявка мгновенно приходит менеджеру в чат, там же остаётся история. Ноль инфраструктуры, бесплатно на Vercel, переживает холодные старты.
2. **Дедупликация 10 минут** по нормализованному номеру: по умолчанию in-memory (строго в пределах инстанса), а при заданном `UPSTASH_REDIS_REST_URL` — атомарный `SET NX EX` в Upstash Redis, то есть строгая дедупликация между инстансами. Слот снимается, если Telegram не принял заявку — человек может повторить.
3. **Локально** (не на Vercel) заявки дополнительно дописываются в `.data/leads.jsonl` — удобно смотреть при разработке; на проде этот шаг пропускается.
4. Сверху — honeypot-поле, rate limit 8 заявок / 10 минут с IP и понятные ошибки.

Итог: менеджер получает заявку мгновенно, клиент — понятный статус, система не зависит от эфемерной ФС.

## 2. Что делал сам, что поручал ИИ

**Сам:** постановка задачи и продуктовая рамка (тон «тёплый, без снобизма», структура блоков, УТП свежести), выбор заголовка «Кофе, который ещё помнит четверг», палитра и типографика (бумага + серифная журнальная пара), подбор и отбор фотографий, архитектурное решение по хранению (Telegram вместо файла/SQLite), сценарии дедупликации и UTM, приёмка каждого этапа: чтение диффов, ручные прогоны формы, проверка текстов, Lighthouse и отказ от неудачных вариантов.

**ИИ под моим управлением:** черновики кода и вёрстки, генерация рутинных частей (типы, тесты, стили), первые версии текстов и конфигов, разбор ошибок сборки. ИИ не принимал решений «за меня»: каждый этап проходил ревью, спорные варианты откатывались (см. п. 3), а тексты переписывались под голос Ани и Дмитрия.

## 3. Где ИИ ошибался и как я это заметил

1. **SQLite на Vercel.** Первый предложенный вариант хранения — файл SQLite рядом с приложением (`docs/ai-drafts/sqlite-store.ts`). Я остановил его на этапе проектирования: на Vercel ФС read-only/ephemeral, дедупликация и история развалились бы. Переделали на Telegram + память/Redis, обоснование выше.
2. **Шаблонный дизайн.** Первый сгенерированный hero — фиолетово-синий градиент, стеклянные карточки и «инновационная обжарка нового поколения» (`docs/ai-drafts/template-hero.tsx`). Это ровно то, что бриф запрещает. Отклонил и пересобрал первый экран в крафтовой бумаге и журнальной типографике, с конкретикой: четверг, пятница, 5 кг, 1–3 день.
3. **Оптимизации, которые всё испортили.** ИИ предложил инлайнить CSS в HTML и «оживить» бумагу SVG-шумом (feTurbulence). В Lighthouse Mobile это дало TBT ~1000 мс и −20 баллов производительности. Убрал оба решения, оставил обычный CSS-файл и чистую бумагу; добавил `content-visibility` на секции ниже первого экрана — TBT упал до ~100–200 мс.
4. **Мелочи, поймавшиеся тестами:** маска телефона сначала принимала номер с лишними цифрами (тест на 10 цифр → исправлено); `react-hooks/set-state-in-effect` при первом варианте чтения UTM (убрал эффект, читаю метки в момент отправки) — тесты и линтер в проекте не для галочки.

## 4. Что не успел / сделал бы за две недели

- Полноценное хранилище и админку: Postgres/Supabase, статусы заявок, экспорт, история клиента — Telegram хорош как канал, но не как CRM.
- Личный кабинет подписки (выбор сортов, пауза, перенос даты) вместо переписки.
- Реальные фото Ани и Дмитрия и съёмку мастерской, страницы «Доставка/оплата/оферта», юридические тексты.
- Аналитику: цели Яндекс.Метрики и GA4, дашборд по UTM, A/B-тесты заголовка и CTA.
- Глобальную дедупликацию и ретраи Telegram через очередь (Upstash/QStash), e2e в CI и деплой на прод.
- Дожать Lighthouse до стабильных 95+ на любом прогоне: лучший прогон 95, но на локальном железе разброс TBT/LCP большой — вынести замер в CI, добавить критический CSS и сабсет шрифтов по фактическим глифам.

## Запуск

```bash
pnpm install
cp .env.example .env.local   # заполните Telegram и (опционально) Upstash
pnpm dev                     # http://localhost:3000
```

Проверки:

```bash
pnpm test                    # 65 unit/интеграционных тестов
pnpm lint && pnpm typecheck
pnpm build && pnpm start

node scripts/lighthouse-mobile.mjs   # сам поднимет сервер, снимет отчёт в docs/screenshots/
node scripts/qa-screenshots.mjs      # Playwright: маска, UTM, дубли, ошибка, скриншоты
```

Без `TELEGRAM_BOT_TOKEN` API работает в dev-режиме: печатает заявку в консоль и пишет в `.data/leads.jsonl`, форма при этом отдаёт успех — удобно проверять локально.

## Деплой на Vercel

1. Импортировать репозиторий как Next.js-проект (Vercel сам подхватит `pnpm`).
2. Переменные окружения: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `NEXT_PUBLIC_SITE_URL=https://<ваш-домен>`, при желании — `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN`.
3. Telegram: `@BotFather` → `/newbot` → токен; написать боту `/start`; `chat_id` узнать через `@userinfobot`.
4. Deploy → проверить отправку формы: заявка должна прийти в чат, повторный сабмит в течение 10 минут — не создать вторую.
